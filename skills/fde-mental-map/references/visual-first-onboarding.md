# 第 0 层：先看见它（Visual-First Onboarding）

## 目的

当学习者说“没有画面感 / 完全看不懂 / 基础薄弱 / 看不懂第二张图”时，不要直接输出完整的多层架构图或一堆命令。先帮对方形成 **物理实体、操作界面和抽象概念** 的空间表象，再逐层连接技术关系。

> **看得见 ≠ 系统一定有独立窗口。** 某些对象是机房里的硬件，有些是系统里的资源，有些是协议/角色；虚拟机、容器与端口并不一定有“能看到的 GUI”。

## 第 0 层的五步教学

1. **真实形态**：它是什么类别？物理设备 / 软件 / 虚拟资源 / 后台进程 / 协议 / 逻辑角色。回答“真能摸到吗？”
2. **在哪里能观察到？** 指出用户在 Mac、终端、云控制台、Docker Desktop、浏览器等界面里可能实际看到什么；说明这个界面只是在管理或观察对象，不等同于对象本身。
3. **单一对象的小图**：先只画 1–3 个组件，优先使用包含框，标注箭头代表包含还是访问。先不混合 Docker、DNS、Nginx、数据库、API 等整条链路。
4. **逐步展开**：每次只新增一层或一条边，让学习者自己能说出“谁运行在哪里 / 谁向谁发送请求”后再继续。
5. **一个小问题确认**：让学习者做 1 道判断，例如“删除容器会删除虚拟机吗？”，根据回答调整下一层深度；不连续考试，不让学习者难堪。

## 示例：服务器 → VM → Linux → Docker → Container

### 看实物

- **物理服务器**：机房机架里能够摸到的电脑，有真实 CPU、内存、磁盘；个人笔记本也是计算机，只是用途不同。
- **VM（虚拟机）**：没有独立的机箱，是虚拟化软件提供的虚拟计算实例。可能在云平台看到一条实例记录，也可能通过远程桌面或 SSH 进入它。
- **Linux**：操作系统。用户可能看到终端提示符、文件目录、进程列表，而不一定有桌面。
- **Docker**：提供容器管理和运行能力的工具；可在终端看 docker ps，或在 Docker Desktop 观察容器（如果已安装）。
- **Container（容器）**：在隔离环境里运行的进程实例，通常没有自己的“电脑桌面”；可通过日志、进程、网络接口和容器管理工具观察。

### 逐层拆开的包含图

先只画：

~~~text
[真实物理服务器]
    ├── [虚拟机 A]
    └── [虚拟机 B]
~~~

接着单独看 B：

~~~text
[虚拟机 B]
    └── [Linux 操作系统]
          └── [Docker]
                ├── [容器 1：后端应用]
                └── [容器 2：Redis]
~~~

图上符号 **└── 表示“运行在里面或由上层环境承载”**，不是用户请求流向。此处是示意架构：真实项目也可能直接用物理 Linux 主机运行容器，不需要 VM；也可能不用 Docker。

### 对象与界面别混淆

| 对象 | 能否摸到 | 用户可能在哪看到 | 容易误解 |
|---|---|---|---|
| 物理服务器 | 能 | 机房、设备管理平台 | “服务器一定有显示器” |
| 虚拟机 | 不能单独摸到 | 云控制台、虚拟化平台、远程终端 | “虚拟机就是 Docker” |
| Linux | 软件 | SSH 终端、命令输出 | “有 Linux 就一定有桌面” |
| Docker | 软件平台 | 命令行、Docker Desktop | “Docker 本身就是一个网站” |
| 容器 | 运行实例 | 容器列表、日志、进程 | “容器必须像 Windows 一样有窗口” |

### 最小验证题

问：“如果我删掉一个 Docker 容器，是不是同时删除了它所在的 Linux 虚拟机？”

答：通常 **不是**。被删的是容器实例，不是承载它的虚拟机；容器内未持久化的修改可能丢失，正确保留并挂载的数据卷可能仍在。下一步再引入 Volume。

## UI 与图片的使用原则

- 若当前环境支持可信图片搜索、真实截图或图形展示，并且图像确实能帮助初学者，优先给 **实物照片或真实界面**；不得伪造某客户系统当前界面的截图。
- 无法展示真实图片时，明确说明并采用“你可能在屏幕上看到什么”的文字布局、表格及小图，仍可完成第 0 层教学。
- 用户提供截图后，先说明截图中可见的具体区域，再对应到概念与架构层。不要从一张截图推断看不到的部署拓扑。
- 一个复杂问题最多先展示一张最小示意图；理解后再给完整图。图中标注图例：“方框嵌套＝包含；实线箭头＝网络请求；虚线箭头＝异步任务”等。
- 不要把“图更好看”放在“关系是对的”之前。

## “推导”式教学节奏

以**我们看到什么 → 为什么需要这个东西 → 它在哪 → 与谁发生什么关系 → 如果缺了会怎样 → 出错如何验证**推进。每一步都衔接上一层，不突然引入 8 个全新名词。

例如：

1. “服务器是一台主要提供服务的电脑。”
2. “一台很强的电脑想隔离多个项目，于是可使用虚拟机。”
3. “虚拟机本身有操作系统，常用 Linux。”
4. “应用依赖不一致会影响部署，Docker 可以帮助打包与管理容器化应用。”
5. “每个容器内可以运行一个服务；删掉某容器不代表删掉整台虚拟机。”
6. “等理解包含关系，再切换到用户请求如何跨 IP/端口到达应用的另一张地图。”

**停止标准**：对方能描述一个对象的形态、观察入口、所处层级，并说出最常见的一个边界（删除容器不等于删除 VM；容器 Running 不等于公网可达）。
