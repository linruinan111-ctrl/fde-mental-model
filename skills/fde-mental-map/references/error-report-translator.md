# 把技术报错翻译成人话：FDE 排障翻译模式

## 什么情况用这个模式

当用户贴进来一段 AI 分析、终端错误、日志、网络检测结果，表示“看不懂”时，先启用本模式。不要直接罗列更多术语，也不要把别人猜测的结论当成事实。

目标：让用户说清 **谁在做什么、在哪一步出问题、哪些事实已知、下一步如何安全检查**。

## 六步讲解节奏

1. **先还原现场**：有几台电脑、哪些网络、谁访问谁？把用户 Mac、远程服务器、AI 测试沙箱等画成不超过 3–5 个对象的小图。
2. **一句话说出问题**：不用英文缩写，例如“你已经知道网站的地址，但还没成功打开页面”。
3. **逐词翻译**：每次只介绍 1–3 个非懂不可的词：中文解释、小比喻、它处在图里的哪里、比喻哪里不准确。先解释再放入全链路。
4. **给 AI 的断言分类**：分成“实际看到/报告的结果”“合理但未验证的猜测”“证据不足的断言”“缺失的信息”。遇到“一定、可以确定、肯定不是”重点核对证据。
5. **建议一个最小、低风险验证**：说明在哪台机器/哪个界面做、看见什么、该结果能排除什么；没有授权就不执行网络探测、爬虫或修改生产服务。
6. **一个小问题确认理解**：例如“DNS 解析成功，能不能说明网页一定能打开？”用户理解后，再引入下一层。

如果用户只问一句话是什么意思，回答那一句即可，不要把模板全展开。

## 示例：远程网站打不开，另一位 AI 却说肯定不是封 IP

### 看见有几条不同路径

~~~text
你的 Mac + Wi-Fi -------> 网站入口
你的 Mac + 手机热点 ----> 同一网站入口
AI 自己的沙箱 ----------> 同一网站入口
~~~

这是三次不同网络条件下的访问。不能把某个环境的测试结果当成所有环境的共同事实。

### 翻译常见词

| 词语 | 人话 | 成功/失败究竟能证明什么 |
|---|---|---|
| DNS | 查网站名字对应的网络地址 | 查到地址，不代表网页一定能开 |
| IP | 网络上用于寻找目标的地址 | 知道地址，不保证网络可达 |
| TCP | 先建立基础通信连接 | TCP 连上也不代表 HTTPS、网页或登录正常 |
| 端口 443 | 常见 HTTPS 服务的入口编号 | 端口能连上不等于整个站点可用 |
| TLS 握手 | 建立加密通信并做身份验证的过程 | 失败不一定是反爬，也可能是其他网络/协议问题 |
| timeout | 规定时间内没有得到所需响应 | 无法单凭它确定是路由问题或封禁 |
| reset | 网络连接被中断或重置 | 未必知道谁中断、为何中断 |
| IP ban | 根据来源 IP 限制访问 | IP 封禁也可能通过丢包表现为超时 |
| Sandbox | AI 运行任务的受限环境 | 其联网出口不一定与你的 Mac 相同 |
| VPN | 经受控通道连接到其他网络 | 并不是解决全部连接问题的万能钥匙 |

### 识别不够严谨的推断

- “Wi-Fi、热点都打不开”：减少了“只针对原 Wi-Fi 单一 IP 封禁”的可能性，**不能排除**整个 IP 段、地区、网络策略限制，也不能确定路由损坏。
- “TCP 通，TLS 被 reset”：说明所报告的环境在下一阶段连接失败，**不能由此直接断定**一定是 TLS 指纹反爬。
- “AI 沙箱 TCP 通”：只能说明其报告中的沙箱出口到目标端口当时可达，不能证明用户 Mac 的可达性。
- “ping / traceroute 不通”：这类探测可能受到网络设备限速或拦截，**不一定证明**真正的 HTTPS 业务链路一定断了。
- 没看到真实日志或原始输出时，使用“该 AI 报告称”，不要擅自说成“我已经测试证明”。

### 初学者先做什么

先问：浏览器是“首页打不开”，还是“能打开但登录失败”，或者“登录以后数据看不到”？记录可见的错误文字、发生时间和使用的网络。

如果是页面无法打开，下一步再根据具体错误决定检查 DNS、TCP、TLS 还是代理。不要让初学者一开始连续执行十几条陌生命令，更不要未经授权修改生产配置、使用绕过保护的代理或重试爬虫。

## 通用安全规则

- 不把一段 AI 解释里的猜测当作事实；不臆造真实服务器、客户网络或安全策略。
- 用户没有基础视图时，优先应用 visual-first-onboarding.md 的“先看见它”，再进入网络流程。
- 命令必须说明执行机器、目的、可观测结果、风险；先只读。
- 对 Token、密码、Cookie、公司数据、HAR 进行脱敏；不绕过认证或访问控制。
- 最后提醒用户“已经知道什么、还不知道什么、下一步最值得确认哪一个事实”。
