# Mental Model：为什么、在哪里、怎样流动

## 0. 看见系统，再认识术语

对刚入门、没有系统画面感的用户，先阅读 [visual-first-onboarding.md](visual-first-onboarding.md)：

- **外观**：这是物理机器、软件、虚拟计算机、后台进程还是协议？
- **界面**：在机房、Mac 桌面、云控制台、终端或 Docker Desktop 里能看到什么？看不到的是什么？
- **局部视图**：先画出物理服务器包含两台 VM，然后只打开其中一台 VM 的 Linux / Docker；不要上来列出八个并不在同一层的名词。
- **逐步推导**：从“熟悉的电脑”推演到“服务器”；从“共享物理资源”推演到“虚拟机”；从“运行隔离应用”推演到“容器”。
- **确认理解**：只问一个简短判断题，能答对后再切换到下一张地图。

复杂图是学习过程的终点，不是起点。

## 用五种关系连接技术

- **包含 / 运行在（runs on / inside）**：虚拟机运行在虚拟化平台上，Linux 容器共享宿主机内核。
- **通信 / 调用（talks to）**：浏览器通过 HTTPS 连接到服务器；应用调用 Model API。
- **逻辑依赖（depends on）**：某功能需要数据库或缓存，但并不代表它们部署在同一台机器。
- **读写（reads / writes）**：后端查询 SQL 数据库，文件通过 OSS API 存储。
- **发布 / 控制（builds / deploys / orchestrates）**：GitHub Actions 运行发布任务，Agent 调度工具执行。

箭头必须说清是哪一种关系，不能把“云服务器 → Nginx → Docker → 数据库”当成所有项目的请求路径。

## 建立地图的 0+8 个提问

0. 我在现实和软件界面里能看到什么？它在哪里？
1. 是什么？为何被发明？
2. 它位于系统的哪一层？
3. 上游和下游分别是谁？
4. 请求、数据、状态如何流动？
5. 最常见的失败点在哪里？
6. 我该如何缩小排查范围？
7. 方案之间的成本、风险、复杂度取舍是什么？
8. 学到什么程度对 FDE 足够？

## 解释模板（简短，按需扩展）

**一句话定义**：说清本质，不用另一组陌生术语解释。

**系统地图**：
~~~text
入口 ---[网络调用]---> 网关 ---[转发]---> 应用
                                       |--[读写]--> 数据库
                                       |--[调用]--> Model API
~~~

**一次真实业务的旅程**：从用户动作走到结果。明确在哪里保存状态、发生故障怎么追踪。

**三步排查**：症状 -> 可能断点 -> 最小只读验证。需要区分“证据证明了什么”和“无法证明什么”。

**FDE 沟通**：列 2–4 个可向专业工程师确认的精确问题，避免只问“现在怎么办”。

**停止标准**：我能独立解释上下游、提出验证方法、评估方案风险即可；低频的命令可随查随用。

## 学习层级

- L0：听过名字。
- L1：能说出它是什么、为何存在。
- L2：能画所在系统、上下游和数据流。
- L3：能根据现象定位层级、比较方案、审核 AI 输出。
- L4：能负责设计与复杂生产变更。

对跨领域 FDE，多数新技术优先达到 L2–L3；对工作职责内关键组件再深入 L4。

## 判断与执行

**自己必须懂**：访问控制、数据边界、设计取舍、证据判断、故障影响、回滚和验收标准。

**AI 可以辅助**：查询命令、配置样板、代码语法、日志归类、文档查找和重复性任务。

**必须审慎或升级给专家**：生产数据库删除/迁移、权限体系修改、网络边界变更、安全事故、无法回滚的操作。

## 教学互动

首次出现术语先解释中文和英文缩写。一次优先引入 3–5 个核心概念，不要堆满专业名词。能用具体客户项目举例就用客户项目；但不能臆造客户的实际架构、账号、IP 或配置。
