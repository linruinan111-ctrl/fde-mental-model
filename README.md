# FDE 技术地图：让 AI 把技术讲明白

> **不是教你背命令，而是帮你在脑子里慢慢搭起一张图：电脑在哪里、程序在哪里、请求怎么走、出错在哪里。**

如果你正在做 FDE，但经常有这些感觉：

- 别人说“服务在另一台虚拟机上”，你每个字都认识，却想象不出那是什么。
- 你听过服务器、Docker、SSH、Nginx，可是完全不知道它们怎么联系起来。
- AI 发来一大段 DNS、TCP、TLS、IP 被封、timeout 的分析，你还是不知道该从哪里查。
- Codex 能帮你把程序跑起来，但你不知道它到底动了什么。

**这个小工具就是给这种场景准备的。** 完全不需要你先懂 Linux 或编程，先学会“看懂现场”就可以。

---

## 1. 先说清：这到底是什么？

这是一个给 **Codex（帮助你写代码、运行命令的 AI 助手）** 使用的教学说明书，名字叫 **fde-mental-map**。

这类可复用的 AI 说明书通常叫 **Skill（技能）**。

- **这个 GitHub 仓库**：存放说明书的地方，可以理解为网上的项目文件夹。
- **README**：就是你现在看的“使用说明”。
- **SKILL.md**：真正告诉 Codex “应该怎么教你”的核心文件。
- **references 文件夹**：给 Codex 参考的例子和术语解释。

安装 Skill 后，你可以在 Codex 里输入：

~~~text
$fde-mental-map SSH 是什么？它在哪里？我在 Mac 上怎么看到它？
~~~

Codex 就会尽量从你看得见的东西开始解释，而不是上来讲一长串英文。

**注意：Skill 不会自动帮你连上公司服务器，也不会自动改生产环境。** 它的作用是改变 AI 讲解和分析问题的方法。

## 2. 它会怎么教你？

最重要的原则是：**先看见，再理解，再连接，最后才考虑操作。**

### 第 0 步：先让我“看见”

先说这东西是什么形态，在哪个界面能看到。

比如你问“服务器、虚拟机和 Docker 到底是什么”：

~~~text
先想你自己的 Mac：一台真实电脑。
  ↓
服务器：另一台主要用来运行服务的电脑。
  ↓
虚拟机：通过软件创建的一台“虚拟电脑”。
  ↓
Linux：这台虚拟电脑可能使用的操作系统。
  ↓
Docker：运行在系统里的容器管理工具。
  ↓
容器：用于运行具体程序的隔离环境。
~~~

**你不必一下子理解全部。** 理解“物理服务器和虚拟机的关系”，再学下一层。

### 第 1 步：用人话解释“它是什么、为什么要它”

比如，不先背 Docker 的命令，而是先想：“为什么开发人员的电脑上能运行，放到服务器上却不行？Docker 希望解决其中哪些问题？”

### 第 2 步：只画一张你能理解的小图

先画：

~~~text
[一台真实物理服务器]
       ├── [虚拟机 A]
       └── [虚拟机 B]
~~~

你能理解后，再看虚拟机里面的 Linux 和 Docker。

注意：上面的方框表示“运行在哪里”，**不是**“浏览器请求会先经过谁”。

### 第 3 步：把一次操作走一遍

例如“你打开网页”：你的电脑先找到网站地址，再尝试网络连接，最后请求页面。不要在没有基础时就画一整张复杂的网络图。

### 第 4 步：出现故障，先找哪一关出错

比如网站打不开，先分辨是“完全打不开首页”，还是“首页能打开但登录失败”。不同现象意味着不同排查方向。

### 第 5 步：只学到工作需要的程度

作为 FDE，你应该能说清楚系统大致如何运行、提问和判断 AI 的回答；不必为了偶尔使用 Docker，就背下所有 Docker 命令。

## 3. 新增：把 AI 的“天书解释”翻译成人话

你可以直接把别的 AI 给你的一大段话或一张报错截图发给 Codex：

~~~text
$fde-mental-map
这段 AI 的故障分析我完全看不懂。
请先告诉我：现场到底有哪几台电脑，谁在访问谁？
再一个一个翻译术语，画一张最小的图。
把“已经证实的事实”和“AI 猜的原因”分开，不要一次塞给我十个概念。

[把报错内容或已经脱敏的日志贴在这里]
~~~

例如，AI 说：

> DNS 正常，TCP 443 能连，但 TLS 握手 reset，所以可以确定不是 IP 被封。

Skill 会让 Codex 这样拆开讲：

| 原话 | 换成人话 |
|---|---|
| DNS 正常 | 这个测试环境找到了网站的网络地址 |
| TCP 443 能连 | 这个测试环境尝试建立基础网络连接，报告称成功 |
| TLS 握手 reset | 下一步建立加密通信时，连接中断了 |
| 所以肯定不是 IP 被封 | **这个结论还不能确定**；一种现象可能有不止一种原因 |

它还会提醒你：AI 自己的测试电脑和你的 Mac **可能走的是不同网络**。不能拿一个地方的结果替另一个地方下结论。

要学会的不是“立刻猜出根因”，而是区分 **看见了什么 → 这能说明什么 → 还需要验证什么**。

详细规则见：[报错翻译指南](skills/fde-mental-map/references/error-report-translator.md)。

## 4. 想立刻试试？复制下面这句话

如果你已经在 Mac 上装好了这个 Skill，打开 Codex，粘贴：

~~~text
$fde-mental-map
我是技术零基础的 FDE。
请从我的 Mac 电脑讲起：服务器、Linux、虚拟机、Docker 到底是什么？
先让我知道它们在现实里是什么样、在哪个界面能看到。
每次只讲一层，别急着讲命令。讲完问我一个小问题确认理解。
~~~

你也可以换成自己工作中的问题，例如：

- “为什么 Docker 显示容器 Up，我却打不开网站？”
- “我已经 SSH 进 Linux 了吗？我输入的命令会在 Mac 还是服务器上运行？”
- “Codex 说 CI 通过了，但页面为什么还是旧的？”
- “Windows Agent、Gateway、Worker 到底谁在谁里面，任务怎么走？”

## 5. 如何安装到 Mac 的 Codex？（小白路线）

**不用下载 ZIP，也不用你手动一个个建文件。**

最简单的方法：打开 Codex，把下面整段话发给它，让它协助你在自己的 Mac 上安装。

~~~text
请帮我安装这个个人 Skill：
https://github.com/linruinan111-ctrl/fde-mental-model

真正的 Skill 文件夹在：skills/fde-mental-map/

请先只读检查仓库内容，再把它安装到我自己的 Mac：
~/.agents/skills/fde-mental-map/

如果本地已有同名文件夹，不要覆盖，先告诉我怎么安全更新。
不要修改公司项目，也不要在远程 Linux 服务器上安装。

安装后请运行仓库中的 scripts/verify.sh 做文件检查。
然后告诉我如何在 Codex 中使用 $fde-mental-map。
~~~

**这里有两处你需要知道：**

- 这个路径前面的 **~** 代表你的 Mac 用户主目录；不是 GitHub 上的路径，也不是公司服务器。
- 如果 Codex 提示要批准某个文件操作，先确认路径是你自己的 Mac 用户目录，不要盲目批准修改生产环境。

### 想自己在终端里安装？（可选）

下面三段命令都是在 **Mac 本地终端**运行，不是在 SSH 登录的公司服务器上。

**① 把网上仓库复制到 Mac：**

~~~bash
git clone https://github.com/linruinan111-ctrl/fde-mental-model.git
~~~

**② 进入刚刚复制的文件夹：**

~~~bash
cd fde-mental-model
~~~

**③ 安装，并检查需要的文件有没有在：**

~~~bash
bash scripts/install.sh
bash scripts/verify.sh
~~~

安装脚本不会覆盖已经存在的同名 Skill。若提示 Already exists，意思是你可能已经装过，**不要为了重新安装就直接删除旧文件**。

安装结束后，重新打开或刷新 Codex，再试一次第 4 节的提问。

注意：文件检查成功只说明文件齐全；最终还需要在 Codex 中实际调用一次，才能验证 Skill 已被识别。

## 6. GitHub 更新了，我本地的 Skill 会自动变吗？

**不会。**

想象你把网上的一份教材复制到了 Mac 上。作者后来改了网上的教材，你电脑里的旧副本不会自己变化。

你可以请 Codex 帮你更新。直接复制：

~~~text
请帮我更新我本地的 fde-mental-map Skill。
仓库：https://github.com/linruinan111-ctrl/fde-mental-model

先检查线上新版和我本地旧版有什么不同。
如果有我自己修改过的内容，请先备份并告诉我。
确认安全后再更新 ~/.agents/skills/fde-mental-map/。
更新后验证所有参考文件都齐全，再用一个简单问题测试 Skill。
不要修改其他项目或服务器。
~~~

如果你还没在本地安装，就按第 5 节进行首次安装，不用更新。

## 8. 两个特别重要的提醒

**第一，不要把工作资料直接传到公开 GitHub 仓库。** 目前这个仓库是公开的；不要提交公司代码、客户信息、账号密码、Cookie、Token、API Key 或包含真实凭据的日志。遇到敏感内容先脱敏。

**第二，AI 能解释，不代表它的推断一定正确。** 这个 Skill 会强调“事实、猜测、还没确认的部分”，但不保证 AI 永远不会出错。真的涉及公司服务器、数据库或生产部署时，先弄清操作会影响哪里，再决定是否执行。

## 最后：你不需要先成为运维工程师

这个项目的目的，是让你每学一个新词，都能慢慢回答四个问题：

**它是什么样？在哪里？和谁有关系？出问题先检查哪里？**

懂了，再向下一层走。不要因为 AI 会执行命令，就跳过自己的判断；也不要因为一张架构图看不懂，就逼自己一次学完所有东西。
